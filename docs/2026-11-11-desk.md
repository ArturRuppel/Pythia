# The desk — what the owner has validated

**Status:** built · **Date:** 2026-11-11 · replaces the reading list (`[curation] active`, `lit
curate`, the board's WIP panel, the app's Reading tab)
**Companions:** [SCHEMA.md §4](../SCHEMA.md) (`validated`, its validation) ·
[CURATION.md](../CURATION.md) (agents never write it)

## Why a second number

`pass` (0–4) says how far curation ran on a paper. It used to be raised one rung at a time with
the owner in the loop, so it also said how deeply the owner had engaged with the paper. Batch
curation broke that: agents now raise it for many papers at once. The owner does not read slices
or the map; they want one signal per paper. So each curated paper carries a second number,
`validated`, the pass the owner has validated. It is the owner's alone: written by
`lit validate` or the viewer's Validate action, never by `lit ingest` and never by curation.

Absent means the owner has never validated the paper at any depth, which is every newly
ingested paper. `validated: 0` means the owner knows the paper is in the library, unread.

## The desk

The desk is derived, never stored:

> on the desk iff `validated` is absent, or `validated` != `pass` (an absent `pass` counts as 0)

Two groups: **new** (never validated) and **changed** (validated N, curation now at M). An agent
that rewrites a paper at the *same* pass leaves it off the desk; only a change of `pass` puts it
back. `validated` above `pass` is legal (the owner read further than curation ran) and flagged by
`lit build`, never an error.

The reading list it replaces had a backlog and mixed two meanings, "come back to this" and "this
is being curated". The desk has neither problem: it empties itself as the owner validates, and it
refills only when curation moves.

## Validating

- **Validate** sets `validated` to the pass the viewer *shows*. The client always sends that
  number (`POST /validate {citekey, pass}`), so if an agent raised the pass after the page loaded,
  the owner validates what they saw and the paper stays on the desk at the new pass. Without a
  number (the CLI's default) the server takes the pass on disk at write time.
- **A lower level** is offered beside it: the pass labels below the current pass (0 ingested ·
  1 abstract · 2 intro+disc · 3 results · 4 methods), minus the one already validated, for a paper
  read less deeply than curation ran.
- The write edits one line of `curated/<citekey>.yaml` and leaves every other byte alone: an
  existing `validated:` line is set in place (its comment kept), a new one goes directly under
  `pass:` and that line's own wrapped comment, or where `pass:` would be. A layout the line edit
  does not recognise falls back to the ruamel round trip `lit tag` uses.
- It settles in place with no reload: the card's status swaps, the desk pill recounts, the app's
  row leaves the list. Validating changes a status, never a card or an arrow, so there is nothing
  for a reload to settle. A failed POST says so and leaves the control live for a retry.
- `lit serve --read-only` refuses `/validate`: the field lives on the paper's own synced file.

## Where it shows

**Status everywhere is the validated pass.** The app's meter and the board's pie show
`validated`, with a quiet marker when the owner has not caught up: "new" for a never-validated
paper, "curated M" when curation ran ahead. The library sorts by it ("Validated pass"), the board's
landing column ranks by it (then by `pass`, so before any validation the order is unchanged), the
walk prints it. Nothing shows the curation pass as a paper's status any more.

- **App: the Desk tab** (Library · Topics · Desk · Search). The two groups, newest curation record
  first (the YAML's mtime is the only date a paper carries), each row the library's own row with
  its status line ("new · curated M label" / "validated N · curated M") and the Validate controls
  under it. Collection chips narrow it. The paper page carries the same controls under its status.
- **Board: the "desk · N" pill** opens the same list; ✓ on a row validates at the current pass, a
  row click finds the paper (gotoPaper). Right-click a curated card → Validate, or a lower level.
- **Offline and static.** The desk is derived from the payload, so the offline copy and a
  `lit build` file list it too. Offline, the Validate controls stay in place, disabled, with one
  line saying why; a static build shows none.
